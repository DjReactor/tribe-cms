# tribe-cms

Parent: `../AGENTS.md`

## Purpose

The per-client product: a public marketing website plus a Business-Owner (BO) dashboard. This is the artifact deployed once per client instance. Next.js 16 (App Router, Turbopack) / React 19 / PocketBase backend / Tailwind 4, with BlockNote rich-text, Mantine, framer-motion, and react-hook-form + zod. Version 0.4.0.

## Ownership

Owns the public site, the BO dashboard, the PocketBase schema/migrations/seed, the template engine, and the on-VPS deploy pipeline. This is a **git submodule** — edits here commit to the `tribe-cms` repo, not the parent.

## Local Contracts

- App Router under `src/app/`:
  - `(public)/` — public site: home, about, services, service-areas, `[area-slug]`, projects, locations, `locations/[slug]`, types, brands, certifications, awards (each catalog section: index + `[slug]` detail), blog, testimonials, contact, privacy-policy, terms-of-service.
  - `dashboard/` — BO admin: blog, business-info, call-logs, content, crm (incl. contact-detail `crm/[id]`: unified activity timeline + per-contact deal management + manual compose), deals, analytics, design, locations, media, projects, types, brands, certifications, awards (the four catalog sections are thin wrappers over shared `catalog/actions.ts` + `components/dashboard/catalog/`), landing-pages (incl. `landing-pages/new` and `landing-pages/checklist`), security, seo, service-areas, services, states, settings (incl. `settings/agency`, `settings/lead-sources`), testimonials (server logic in `dashboard/actions.ts`).
  - `api/` — `auth`, `contact`, `internal`, `tribe`, `webhooks`.
  - `login/`, plus `sitemap.ts`, `robots.txt/route.ts` (route handler, not the metadata file — appends the BO-editable `custom_robots_rules` verbatim), `sitemap-images.xml/`.
  - SEO wiring: redirects (`redirects` — `from_path`/`to_path`/`type`, hit-counted) are applied in middleware before routing (they take precedence over live pages) from a 30s in-memory cache fed by `api/internal/redirects` (Bearer `INTERNAL_SECRET`). 404s are logged to `seo_404_log` (`hit_count`/`last_seen`/`resolved`, unique on `path`) by the `Track404` client beacon on the 404 page → POST `api/track-404`. **Gotcha: the root `not-found.tsx` must stay side-effect free and must not use request APIs** — Next.js renders it speculatively during ordinary 200 requests, so server-side logging there counts every page view as a 404 (this shipped broken in 0.4.1 and was reverted). Schema reconciled in migrations `1960000000` + `1970000000`. **All writes go through `src/lib/redirects.ts`** — `syncSlugRedirect` / `syncSlugRedirects` (upsert old→new, then re-point anything that already pointed at the old path so a twice-renamed slug leaves one hop rather than a chain, deleting any rule that would end up pointing at itself) and `clearRedirectShadowing(...paths)` (drop rules aimed at a path a live page now occupies — middleware runs *before* routing, so a stale rule makes a real page unreachable). Everything there is best-effort and swallows errors: a missing redirect is a broken old link, not a failed save. **`redirects.source` / `.destination` are vestigial** — `1960000000` moved the meaning to `from_path`/`to_path` but left the originals `required: true`, so every row the app tried to create failed validation ("source: Cannot be blank"): the manual redirects UI errored on every rule, and the automatic service-slug rule failed silently inside its own `catch`. Migration `2050000000` makes them optional; the columns are kept because they hold the pre-reconciliation values. Never write them.
- **Dashboard write-path rule:** the BO session is a regular `users` record, so a server action may write with the cookie client (`getPocketBaseClient`) only if the target collection's write rules are `@request.auth.id != ''` in committed migrations (most content collections, via `1780775943` or their create-migration). Collections with `null` (superuser-only) write rules — `contacts`, `api_keys`, `redirects`, `seo_404_log`, `event_outbox`, `legal_pages`, `settings`/`seo_settings` *creates*, plus cross-user `users` updates — must be written via `requireAuth()`/`requireAgencyAdmin()` then `getAdminPocketBase()` (writing them with the cookie client fails with "Only superusers can perform this action"). Reads may stay on the cookie client except `api_keys` (list/view are also superuser-only).

Catalog datatypes (`1990000000`): originally four identical-schema collections; `types` was dropped by `2020000000` (see below), leaving `brands`/`certifications`/`awards` (name, slug, description, `details` BlockNote json, `image_url`, is_active/sort_order, SEO fields) + their `*_enabled` settings switches; shared shape is `CatalogItem` in `src/types`, fetchers in `src/lib/catalog.ts` (per-switch gating, arrays passed globally to all template pages like locations/projects), kind whitelist in `src/lib/catalog-kinds.ts`. Business hours (`business_info.hours`, json): edited in `dashboard/business-info` (per-day Open/Closed + single range + "Open 24 hours"); times are stored canonical **24-hour `HH:MM`** (not 12h display strings — those break the schema.org `OpeningHoursSpecification` in `seo.ts`, which needs ISO-8601 Time; `open24` ⇒ 00:00–23:59) and formatted to 12h only for display (`components/shared/BusinessHours.tsx`). Migration `2000000000` backfilled legacy `"08:00 am"` records to 24h. Migration `2050000000` relaxes the vestigial `redirects.source`/`.destination` (see the SEO wiring bullet). JSVM migration gotchas: a live field's `type` is a method (`f.type()`); mutating a field *property* in place **does** persist (`field.required = false` then `app.save(collection)`, verified by a `2050000000` up/down round trip) — it is renames specifically that do not, and a rename has to be add + backfill + drop — add the new field, backfill with a raw SQL column copy, *then* drop the old one (that order, not drop-first, means an interrupted run leaves both columns rather than destroying data; backfill only where the destination is still empty so a re-run cannot clobber later edits — see `2040000000`).
- Automation/outbox (Automation & CRM plan, Phase 1): outbound events to n8n flow through `src/lib/automation.ts` — `dispatchEvent()` enqueues an HMAC-signed envelope (plan §5.1) into the durable `event_outbox` collection (migration `1870000000`, admin-only) and delivers best-effort; failures retry with backoff. SSRF-guarded by `settings.automation_allowed_host` (falls back to legacy `lead_webhook_*` for one release). A per-instance PM2 worker `scripts/drain-worker.js` (process `tribe-${SLUG}-drain`) polls `api/internal/outbox/drain` (Bearer `INTERNAL_SECRET`) to drain the backlog; `dashboard/outbox` (agency-admin) surfaces status counts + failed/dead rows with a retry-all action. Emitters: `api/contact` emits `lead.created` directly; `deal.created`/`deal.stage_changed`/`deal.won`/`deal.lost` and `contact.lifecycle_changed` are emitted from the shared `src/lib/crm-writes.ts` helpers (called by both `dashboard/{deals,crm}/actions.ts` and the inbound CRM API), so the dashboard and n8n produce identical activity + event side-effects. The Retell webhook (`api/webhooks/retell`) emits `call.completed` once a call is analyzed. The contact-detail compose box (`crm/[id]` → `requestMessageSend`) emits `message.send_requested`; n8n sends and logs the outbound back via `api/internal/crm/messages`.
- CMS-native lead notifications (Automation & CRM plan §12): on a new contact-form lead, `src/lib/notifications.ts` sends up to four immediate single-shot notifications (owner/lead × sms/email) through typed provider adapters (Twilio form-encoded/basic-auth, Telnyx JSON/bearer, Postmark JSON/token — plain fetch, no SDKs). Delivery reuses `event_outbox` via a `kind` field (`webhook` | `notification`; `deliverOne` branches) with the same backoff/dead semantics; permanent config/consent failures go `dead`, provider errors retry. Lead-facing sends log `messages` rows; owner sends log `activities` rows (`type: owner_notified`) — both surface on the contact timeline. **Config is agency-admin-only** (§12.2): the 20 `AGENCY_ONLY_SETTINGS_KEYS` (toggles, destinations, provider creds, templates, `sms_consent_text`, `automation_custom_headers`, `automation_context`) are stripped from the generic settings actions and managed solely by `dashboard/settings/agency/notifications-actions.ts` (requireAgencyAdmin; secrets masked `••••`+last4; blank/masked write keeps stored value) + `LeadNotificationsCard` (incl. per-channel send-test). Do NOT map these into `getSettings()`/`TemplateSettings`.
- SMS consent (TCPA, §12.3): the shared `ContactForm` fetches the disclosure via `GET /api/contact` (server-rendered from `sms_consent_text`/default + business name — displayed text is byte-identical to what gets recorded) and shows an unchecked-by-default checkbox; no text ⇒ no checkbox ⇒ no consent. `POST /api/contact` stores the denormalized gate on the contact (`sms_consent`/`sms_consent_at`) and an APPEND-ONLY `consent_records` proof row (verbatim text, page URL, IP, UA; reserved empty `replay` file field for future TrustedForm/rrweb evidence). The lead-ack SMS enqueues only with consent and re-checks it at send time. Never update/delete `consent_records` rows.
- Outbound envelope extensions (§12.8): the webhook lane merges `settings.automation_custom_headers` into requests (`Content-Type`/`X-Tribe-*` protected from override) and injects a `context` block (business snapshot from `business_info` + free-form `automation_context`, composed at send time) into every envelope. Strict provider APIs must never be pointed at the webhook lane — providers are called only through the `notifications.ts` adapters.
- Inbound CRM write-back API (Automation & CRM plan, Phases 2–3): `api/internal/crm/*` lets n8n write into the CRM — `contacts` (POST upsert by email/phone; `[id]` PATCH), `deals` (POST create; `[id]` PATCH stage/value), `activities` (POST), `messages` (POST, deduped on unique `external_id`; `messages/status` POST). Unmatched inbound messages/calls auto-resolve a contact by phone/email (`findOrCreateContact`). All guarded by `guardCrm` (`crm-api.ts`) — `authenticateWebhook` auth (HMAC, Bearer `INTERNAL_SECRET`, or any `api_keys` row; n8n mints a key in the Security UI) + a per-IP rate limit (429; `CRM_RATE_LIMIT_MAX`/min) — use `getAdminPocketBase`, and canonicalize `select` enums through `crm-api.ts` (400 + allowed list on a miss); `source` resolves via `lead-sources.ts`. Stage/lifecycle changes run the `crm-writes.ts` side-effects. Responses are JSON (`{id,created}` / `{ok:true}` / `{id}`); errors 400/401/404/500.
- Analytics (Automation & CRM plan, Phase 5): `dashboard/analytics` reads PocketBase **view collections** (`analytics_*` — funnel, summary scalars, revenue-by-source, top-referrers, cost-per-job/ROAS by close-month + lead-cohort, call-outcomes, speed-to-lead; migration `1940000000`) for the ROI tiles, plus a `source_spend` Ad-Spend panel (manual monthly spend per source). View SQL must expose a unique `id` (`ROW_NUMBER() OVER ()` or a constant) and `CAST` numeric aggregates (else PB infers `json`); `strftime`/`julianday` work directly on PB date TEXT; views are dropped+recreated for idempotency.
- **Dashboard role split:** the Business Owner sees the **Core** and **Business Info** nav groups only; **Design & SEO** (`design`, `content`, `landing-pages`, `seo`) and **System** (`settings`, `security`, `outbox`) are agency-operated. Three enforcement points must stay in sync: `components/dashboard/Sidebar.tsx` marks those two groups `agencyOnly` (individual items are still gated by `settings.*_enabled` or `agency_admin`); each of those seven route segments has a `layout.tsx` calling `requireAgencyPage()` from `src/lib/dashboard-access.ts` (which `notFound()`s for BOs); and the server actions reachable only from those pages call `requireAgencyAdmin()` rather than `requireAuth()`. `app/dashboard/not-found.tsx` is the dashboard-scoped 404 boundary — without it `notFound()` falls through to the public `app/not-found.tsx`, whose `<Track404 />` beacon would log dashboard paths into `seo_404_log`. **Media Library is deliberately NOT agency-only** — it sits in the Business Info group and stays fully BO-writable (`media/actions.ts` uses `requireAuth`), because the shared media pickers in Projects/Services/Catalog/Business Info depend on it. `security/actions.ts` likewise keeps `updateCredentials` at `requireAuth` (own-account self-service). `app/dashboard/page.tsx` checks the role server-side (`verifySession`) to drop the SEO score card and the SEO setup step for BOs — any new link into an agency-only section needs the same treatment.
- **`types` catalog removed** (migration `2020000000`): it was specified as "types of work/offerings", i.e. a synonym for `services`, and once services gained their own parent hierarchy it categorised nothing services could not. The migration drops the collection and `settings.types_enabled`; its `down` recreates both (records are not recoverable). `brands`/`certifications`/`awards` are unaffected — they are trust assets with a distinct job. A future "type" concept (roof type, system type) belongs as a **field on an existing datatype**, never as a revival of this collection.
- **Service hierarchy** (migration `2010000000`): `services.parent` is a single, non-cascading self-relation, so services form a forest capped at **3 tiers**. Two invariants carry the design and neither is negotiable:
  1. **Slugs are globally unique** (unique index `idx_services_slug_unique`; the migration refuses to create it and logs the offenders if an instance already holds duplicates) **and public URLs are FLAT** — every service is `/services/<slug>` whatever its tier. The hierarchy is expressed in navigation, breadcrumbs (`getServiceTrail`) and the index grouping, never in the address, which matches what actually ranks in this niche and means **re-parenting a service never changes its URL**. The route is a single dynamic segment (`(public)/services/[slug]`) matched exactly against the slug, so **a nested path like `/services/remodeling/kitchen` 404s** — nothing on the site emits one, and the only source of one is an inbound link from a structure a client migrated off, which gets a rule in the redirects UI aimed at the URLs that actually have history. An earlier design specified a last-segment catch-all here and this doc described it as shipped; it never was, and the claim was dropped on 2026-08-20 rather than built (Shani's call). Global slug uniqueness still matters independently: it is what lets the flat address identify a service at all. A composite `(parent, slug)` index would allow duplicate top-level slugs, since SQLite treats NULLs as distinct.
  2. **The depth cap lives in application code** (`MAX_SERVICE_DEPTH` in `src/lib/service-tree.ts`), never in the schema — changing it must not need a migration. It is enforced twice from the same module: the dashboard parent picker filters the options, and `validateParent()` in `dashboard/services/actions.ts` re-checks on save (a moved service carries its subtree, so the test is `depth(newParent) + subtreeHeight(self) <= MAX`).
  `src/lib/service-tree.ts` is pure and server-import-free precisely so the browser picker runs the identical rules; `src/lib/services.ts` adds the cached fetchers. **`getServiceList()` is what every public route passes to templates** — a depth-first `ServiceNode[]` where each item carries `depth`, `children` and a precomputed canonical `path`, so no template ever builds a service URL. Corrupt data degrades rather than disappears: an unresolvable parent (deleted or inactive) and a parent cycle both make `getAncestors` return `[]`, which files the service under the roots at a usable URL — the earlier truncating version silently dropped both members of a cycle off the site entirely. The only save that strands a URL is a service changing its own slug (a parent change cannot, since the URL does not encode the parent), which writes a `redirects` row through `src/lib/redirects.ts`; saves also clear any rule whose `from_path` now collides with a live service path, since middleware redirects take precedence over routing. `settings.services_display_mode` (`auto` | `flat` | `tree`, edited in Platform Settings → Services Layout) picks the index layout; `auto` nests only when a hierarchy exists.
- **Landing pages / `pairs`** (migration `2040000000`; dashboard built, **public route still not built**): a `pairs` record is one service×area landing page at `/{area.slug}/{pair.slug}`. **The key is exactly `service` + `service_area` and nothing else** — never add a third relation. Pairs are **opt-in records, not a computed route**: an unpaired combination 404s, so the page count equals what somebody actually wrote. That is the entire point — Google's spam policy treats city-targeted page families as doorway abuse, and thin-content actions have landed on sites whose per-page copy was uniquely human-written, on volume alone. A future third axis belongs in the page body, not the key. Two unique indexes make this structural rather than a validation rule anyone can forget to call: `idx_pairs_service_area_unique` on `(service, service_area)`, and `idx_pairs_area_slug_unique` on `(service_area, slug)` — scoped to the area because the URL is, so a slug only has to be unique within its own first segment. `slug` is **required** and materialised at write time (defaulting to the service slug, overridable): if blanks were allowed, two blank-slug pairs in one area would collide on the slug index despite having different real URLs. `body` (BlockNote json) is the **publish gate** — empty ⇒ cannot publish. Both relations are `cascadeDelete: false` on purpose: deactivating or deleting a service or area must **auto-unpublish** its pairs and set `auto_unpublished` for the agency to review, never silently delete the record. Collection rules are public read + authed write, but that rule is the **floor, not the policy** — pairs are agency-only (Design & SEO), so server actions must gate on `requireAgencyAdmin()`. `settings.manual_checklist_items` (json, `[{ id, label, description? }]`) holds the agency-defined readiness items that `pairs.manual_checklist` (`{ [itemId]: boolean }`) ticks off; predicated system checks stay in code, only these free-text items are data. It is **not** mapped into `getSettings()`/`TemplateSettings` — it is internal agency data, not a template input.
- **Landing-pages dashboard** (`app/dashboard/landing-pages/`, agency-only — all three enforcement points): list with resolved URL / readiness score / publish switch / `auto_unpublished` flag / delete, a deliberate two-picker creation flow at `new/`, the record editor at `[id]/`, a read-only services×areas coverage matrix, and the checklist-item editor at `checklist/`. Four things here are load-bearing and easy to erode:
  1. **The coverage matrix has no create affordance in its cells, and must not gain one.** A grid of blanks each offering a button is an invitation to fill the grid, and filling the grid *is* the doorway shape. Creation stays one deliberate page at a time; there is no bulk path. Filled cells link to the existing record only. Past `PAIR_COUNT_WARNING_THRESHOLD` (30, in `pair-readiness.ts`) the list and the creator both warn, citing why.
  2. **Readiness splits into two halves on purpose.** `src/lib/pair-readiness.ts` holds six hardcoded predicates in two groups — `support` (a project matching *both* this service and this area, a visible testimonial whose free-text `author_location` names the area, a non-empty `also_serving` on the area) and `copy` (body written, unique H1, unique intro; uniqueness is checked across all other pairs). Only `body` blocks publishing. The module is import-free so the creation flow scores a combination in the browser before any record exists and the editor rescores as you type. The agency-defined half is plain labels with **no logic** — anything that has to be *evaluated* is a predicate and belongs in code, because arbitrary predicates as settings rows means building a rule engine.
  3. **A pair owns only the second URL segment.** Changing `pairs.slug` writes its own redirect row; the first segment moves with the area, and the area's save handles that side. Neither half assumes the other ran.
  4. **The publish gate is `hasBlockContent`, not `body.length`.** BlockNote serialises an untouched editor as one empty paragraph, so a length check would let a blank page publish. Publishing also requires the service and area to both be active, and clears `auto_unpublished` (publishing *is* the agency saying they looked).
  5. **Deleting a service or area that any pair points at is refused, by design.** `pairs.service` / `pairs.service_area` are required relations, and PocketBase refuses to delete a record a required relation references ("Make sure that the record is not part of a required relation reference" — verified against the running binary). Rather than surface that, `deleteService` / `deleteServiceArea` count dependents first and return the sentence in `blockedByPairsMessage()`. **Deactivating** is the supported path: it calls `autoUnpublishPairsFor()` (`src/lib/pairs.ts`) from `toggleServiceActive` / `toggleServiceAreaActive` and from the update actions when `is_active` flips true→false, which unpublishes each published pair and sets `auto_unpublished`. Reactivating never auto-republishes — the flag is a note to a human. That cascade is the one place pairs are written outside the agency-only actions, and correctly so: the BO owns Services and Service Areas, and `pairs`' own write rule permits it.
- **Service Areas dashboard** mirrors Services: per-level `SortableList` tree with a depth-first global renumber after any reorder, a parent picker filtered by `validateAreaParent` (cap 4, excluding self, descendants, and anything without room for the moved subtree's own height), a `states` select, and the `also_serving` tag editor. Slugs get **two** checks on save, both answered with a working suggestion rather than a refusal: not in `RESERVED_ROOT_SLUGS` (areas live at the site root and Next resolves static segments first, so an area slugged `blog` would not error — it would silently sit behind the real `/blog`), and unique across areas (the `New York` state vs `New York City` collision is routine). **An area slug change moves N+1 URLs, not one**: the area *is* the first segment of every landing page beneath it, so `updateServiceArea` reads the pairs at their old address before the update and writes a redirect for the area plus one per pair (this is the only single-field edit in the CMS that relocates a whole branch of the site). A parent change moves nothing — area URLs are flat. `states` is its own BO-facing section in Business Info (`dashboard/states`) — name, code, active, order, no public routes.
- **`service_areas.also_serving`** (renamed from `neighborhoods` in `2040000000`): the tier *below* the area tree — places named to prove coverage but deliberately given no page and never linked. Page-worthy ⇒ its own area record; name-worthy ⇒ a string here. The rename happened because areas now nest 4 tiers, so tier 4 *is* the neighborhood tier and the old name pointed at the wrong thing. It rides the global `serviceAreas` prop to every template, so the rename is template-facing (documented in `Planning Files/template_creator_guide.md`).
- **`ServiceArea.state` is the relation ID, not the record** (`stateRecord?: StateItem` carries the expanded form, matching the `Pair.serviceRecord`/`areaRecord` convention). Areas reach templates straight off PocketBase with no mapper in between, so the type used to promise a resolved `StateItem` that no route ever produced — `area.state.code` would have crashed. No current route expands it, so `stateRecord` is normally `undefined`; expand deliberately if a template needs it. `Project.state` is unaffected: projects go through `mapProject`, which does resolve it.
- Templates live in `src/templates/<id>/` — see child doc.
- **Tree-logic regression net:** `node --experimental-strip-types scripts/check-tree.mts` runs 33 assertions over `src/lib/tree.ts` (cycles, orphans, depth caps, subtree moves, flat paths). There is no test framework here; `tree.ts` is kept import-free precisely so this loads with no build step. Run it after any change to `tree.ts` or to `MAX_SERVICE_DEPTH` / `MAX_AREA_DEPTH`.
- Deploy / build / release scripts live in `scripts/` — see child doc.
- A dual-palette color system is active (see `pb_migrations/*dual_palette*` and `color-palette.ts`).
